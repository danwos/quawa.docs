Konfiguration¶

Das Modell legt fest, was auf welcher Stufe gemessen wird. Um die Ringe zu zeichnen, braucht es von jedem Projekt ein paar Angaben. Diese Seite listet sie auf; das genaue Format, der Runner und die Check-Adapter werden im ersten Umsetzungskonzept entschieden.

Planung¶

  • Aktuelles Ziel = höchste Stufe, die heute gilt; Endziel = höchste aufgeführte Stufe; nicht aufgeführte Stufen sind nicht angestrebt.

  • Eine Stufe schaltet sich per Datum oder per Release ein; die aktuelle Version kommt aus dem neuesten Git-Tag (Stufen lassen sich per Datu... (DEC_SCHEDULED_LEVELS)). quawa vermerkt den Wechsel im Verlauf.

  • Ein Bereich darf dem Projekt vorauseilen (Security früher auf Stufe 3).

Skizze: .quawa/¶

Die Konfiguration ist ein Verzeichnis mit einer Datei pro Bereich; in einer Bereichsdatei sind die Stufen die Struktur, so siehst du, welcher Check ab welcher Stufe laufen muss (Die Konfiguration ist ein V... (DEC_CONFIG_DIRECTORY)). Die Skizze zeigt die Form, nicht das endgültige Format.

.quawa/
  project.yaml        model, levels with dates, scopes
  requirements.yaml
  documentation.yaml
  testing.yaml
  code-health.yaml
  security.yaml
  legal.yaml
  product-ux.yaml
  build-release.yaml

# .quawa/project.yaml
model: 1                     # version of the danwos model
levels:                      # missing level = not targeted
  1: active
  2: active
  3: { from: 2027-03-01 }
  4: { from: release 1.0 }   # version from the latest git tag

# .quawa/testing.yaml – level by level, how this project delivers each measure
1:                           # Sketched
  smoke:       { run: "npm run smoke" }
2:                           # Shaped
  unit:        { run: "npx vitest run", report: reports/junit.xml }
  coverage-30: { from-check: unit, report: coverage/lcov.info }
3:                           # Solid – not defined yet, shown dashed
4:                           # Refined
  mutation-60: { run: "quawa mutate", report: reports/mutation.json }
  flake-rate:  { from-history: unit }
  coverage-80: { from-check: unit }

Im Code bekommt vermutlich jede Messung eine eigene Definitionsdatei, die die möglichen Checks sammelt; welche davon ein Projekt nutzt – die Zuordnung –, ist dokumentiert.

Ergebnisse¶

Ein Lauf schreibt pro Check und Scope ein normiertes Ergebnis: Wert, Zustand, Schwellen, Commit, Tool-Version, Zeit, Link zur Rohausgabe. Der Verlauf ist die Folge dieser Ergebnisse – aus ihm ergeben sich Fortschritt, Regressionen und Flake-Rate.
